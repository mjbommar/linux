## 4. Track B — Time-machine (the differentiator)

The strategic argument: every KVM-in-userspace project has a "fast
syscall path" story. The differentiator the redesign committed to
in `00-vision.md` is **deterministic time-travel record/replay**.
v1 had this working at Phase 1 closure; v2 has none of it yet.

The complete path from substrate-ready (today) to time-travel-ready
is three workstreams, sequential:

### 4.1 #168 — snapshot port

**Status:** NOT STARTED. Designed at memo
`02-workstreams/D-kvm-backend/12-snapshot-forkserver-kvm.md`. v1
archive has working code at `arch/um/backend/kvm-v1-archive/
snapshot.c` (647 LoC).

**v1 public surface to port:**

```c
struct kvm_snapshot;
struct kvm_snapshot *kvm_snapshot_alloc(void);
int kvm_snapshot_capture(struct kvm_snapshot *snap);
int kvm_snapshot_capture_regs_only(struct kvm_snapshot *snap);
int kvm_snapshot_restore_full(struct kvm_snapshot *snap);
void kvm_snapshot_free(struct kvm_snapshot *snap);
void kvm_snapshot_destroy(struct kvm_snapshot *snap);
```

**v1-vs-v2 deltas the port has to handle:**

  - **Per-task vs per-pool vCPU.** v1 had a per-task vCPU lifecycle;
    v2's vCPU pool means the snapshot of "the vCPU that ran task X"
    is a coordinate against the pool member. Capture has to walk
    via `vcpu->last_task == X` to find the right slot.
  - **CPUID/SREGS lazy install.** v1 installed CPUID eagerly; v2's
    lazy first-run path (`cpuid_primed` flag + OSXSAVE-at-first-
    dispatch + XCR0 set) means `restore_full()` has to interact
    with a known-quiescent vCPU. Probably simpler than v1 — restore
    happens at a snapshot boundary, which is naturally quiescent.
  - **XSAVE area size.** v1 used the 512 B FXSAVE shape via
    KVM_GET/SET_FPU. v2's T57 Phase A enabled XCR0.YMM so the YMM
    upper-128 lives in the bigger XSAVE area. Snapshot needs to
    use KVM_GET_XSAVE / KVM_SET_XSAVE rather than the legacy FPU
    ioctls. (This is also Phase B territory for T57; doing it as
    part of the snapshot port might be cleaner than retrofitting.)
  - **TLB / mmu_notifier coherence.** v2's TDP-coherence fixes
    (T31/T32/T33) imply the snapshot's restored TLB state needs an
    explicit flush — v1's flow may not have needed this.

**Sizing:** 600-1 000 LoC port + KUnit cases + selftest re-plumbing.
~3-5 weeks of focused work.

**Acceptance criteria:**

  - `kvm_snapshot_capture()` + `kvm_snapshot_restore_full()` round-trips
    a running guest with bit-identical post-restore state.
  - KUnit cases (the v1 era had `snapshot_basic` /
    `record_basic` / `record_stop_replay_consume` /
    `record_strict_replay` / `record_roundtrip`) re-pass under v2.
  - `tools/testing/selftests/um/snapshot-{kvm-,}smoke` selftests
    pass against v2 (require harness re-plumbing).
  - No regression in any of Track A's gates (substrate, cpython-
    parity, mt-mini, threaded-fork-malloc).

**Sub-sequencing within #168:**

  1. Port `struct kvm_snapshot` + alloc/free skeleton. ~100 LoC.
  2. Implement `kvm_snapshot_capture_regs_only()` (lighter, captures
     GP regs + cr2/cr3/cr4 + selectors). Validate via a unit test
     that captures, modifies vCPU regs, restores, asserts equality.
     ~150 LoC.
  3. Implement full `kvm_snapshot_capture()` adding XSAVE +
     memslot footprint + IDT/GDT/IST. ~300 LoC.
  4. Implement `kvm_snapshot_restore_full()`. ~200 LoC.
  5. KUnit cases. ~100 LoC.
  6. Re-plumb the v1-era selftests against v2. ~50 LoC.
  7. Document in a new memo `02-workstreams/D-kvm-backend/26-snapshot-v2-port.md`.

### 4.2 #169 — record/replay

**Status:** NOT STARTED. Designed at memo
`02-workstreams/D-kvm-backend/13-record-replay-determinism.md`. v1
archive has the working code at `arch/um/backend/kvm-v1-archive/
record.c` (1 597 LoC).

**Determinism budget** (from memo 13):

> The guest's perceived state is a function of:
> 1. Initial state (captured at checkpoint).
> 2. Intra-guest computation (deterministic given 1).
> 3. Sources of nondeterminism: time (RDTSC, MSR_TSC, vvar clock,
>    clock_gettime), random (RDRAND/RDSEED, host /dev/random),
>    interrupts (host signals), syscall results (host state), MMIO.

Record = capture every (3) at record time. Replay = restore (1)
and feed (3) back.

**v1 public surface to port:**

```c
struct kvm_record;
struct kvm_record *kvm_record_alloc(void);
int kvm_record_start(struct kvm_record *rec);
void kvm_record_stop(struct kvm_record *rec);
int kvm_record_replay(struct kvm_record *rec);
void kvm_record_destroy(struct kvm_record *rec);
extern struct static_key_false um_kvm_record_enabled;
void kvm_record_observe_syscall(unsigned long nr, ...);
```

**v1-vs-v2 deltas:**

  - **Syscall observation hook.** v1 had a per-syscall record-
    observe call wired into v1's syscall_class.c dispatch. v2's
    syscall_trap.c needs the equivalent hook in the same dispatch
    arm. The hook should be a static_key_false branch when record
    is off (zero hot-path cost).
  - **Gadget syscalls.** v2 has the LSTAR gadget hot-path for ~11
    syscalls (getpid family). The record hook needs to also wire
    into the gadget body, OR fall back to vmexit-on-record-enabled.
    Memo 13 §"gadget interaction" picks the fall-back approach.
  - **TSC / RDTSC.** v2 doesn't yet trap on RDTSC; record mode
    needs to enable RDTSC exits (`KVM_X86_RDTSC_EXIT` flag), record
    the host's read, replay it. Phase B-like complexity.
  - **Signal-level event recording.** v2's signal queue (D.5-fix-2)
    needs to record SIGALRM arrivals + replay them at the same
    instruction-retired boundary. Non-trivial — requires either
    PMU instruction-retired counter or KVM_REQ-driven replay.

**Sizing:** 1 200-1 800 LoC including the syscall-observe hook
plumbing + a `kvm_record_strict_replay_test` KUnit case. ~6-8 weeks
of focused work.

**Acceptance criteria:**

  - Record a stream of 100 syscalls, replay produces bit-identical
    state transitions.
  - End-of-log → `-ENODATA`; divergence → `-EILSEQ`; replay-rewind
    round-trip works.
  - KUnit case `kvm_record_strict_replay_test` re-passes under v2.
  - Selftest `kvm-record-smoke` passes (existing skeleton).
  - No regression in any Phase J gate.

**Sub-sequencing within #169:**

  1. `kvm_record_alloc` + `start` / `stop` skeleton; `static_key_false
     um_kvm_record_enabled`. ~150 LoC.
  2. `kvm_record_observe_syscall` hook in syscall_trap.c, off the
     static key. ~200 LoC.
  3. Side-buffer for syscall arguments (memo 13 §"payload caps").
     ~300 LoC.
  4. Replay primitive — feed recorded outputs back without
     re-issuing host syscalls. ~400 LoC.
  5. RDTSC trap + record + replay (Phase 2 of #169 if it gets
     scoped down).
  6. SIGALRM event record/replay (Phase 3 of #169; harder).
  7. KUnit + selftest re-plumbing.

May want to split #169 into `#169a` (basic syscall record/replay)
and `#169b` (clock + interrupt determinism) given the size.

## 7. Risks

### 7.1 Time-machine scope creep (HIGH likelihood, MEDIUM impact)

**Risk:** #168 + #169 is 3-4 months on paper but record/replay
historically eats more time than planned (v1 went through 5
iterations before strict-replay worked end-to-end).

**Mitigation:** split #169 into `#169a` (syscall record/replay)
and `#169b` (clock + interrupt determinism); land `#169a` first.
A snapshot-only world (`#168` alone) is already useful for
fork-server fuzzing.

### 7.2 Phase J 24h ratio shy of 99.5 % (MEDIUM likelihood, MEDIUM impact)

**Risk:** the iocheck/seccomp flake class (3/60 in the 2h soak)
suggests some workloads have a noise floor at ~95 %. A 24h run
across more workloads may not reach the 99.5 % bar.

**Mitigation:** the iocheck timeout bump (#23) is the obvious fix.
If after the bump some workload class still flakes, document the
flake floor in the Phase J spec rather than chase it.

### 7.3 LKML review surprise (LOW-MEDIUM likelihood, HIGH impact)

**Risk:** Series 7's reviewers (linux-um maintainers + KVM folks)
ask for refactors the substrate's current shape doesn't support
(e.g. "this should be a per-arch hook" / "this needs to go through
the regular kvm-host module path" / "we want to see proof of an
RFC patch series first").

**Mitigation:** the existing `04-risks/decisions-log.md` D-entries
catalogue every architectural choice with rationale. Pre-empt the
common questions by linking to the relevant D-entry in the cover
letter. Send Series 1 + 4 (backend-ops-abstraction-rfc) early to
prime the maintainer conversation before Series 7.

### 7.4 Host turnover (LOW likelihood, HIGH impact)

**Risk:** the cross-host bench fleet (8 hosts) plus the operator's
single development host is a small denominator. A single host
config drift (BIOS update, microcode bump, kernel host upgrade)
could perturb the perf numbers in ways that look like a
regression.

**Mitigation:** the bench JSON captures `tree_head` per host run.
A new pre-commit run on every host before a perf-claim change
catches drift. The cross-host comparison memo (`bench-cross-host-
2026-05-04-postgadget.md`) is the template.

### 7.5 Solo bus factor (HIGH likelihood, MEDIUM impact)

**Risk:** the project has one primary contributor. State-audit
memos + decisions-log are the bus-factor hedge but they're
read-only knowledge; a second contributor would need 1-2 weeks of
ramp.

**Mitigation:** keep the decisions-log current (D106..D122 done).
The AGENT-PROMPT.md + STATUS.md + this PLAN doc are the
onboarding triangle. The agentic-work scaffolding (Opus sub-
agents) is a hedge: a sub-agent walking the memos can carry
investigation continuity if a session is interrupted.
