# UML v2 upstream emission boundaries — 2026-07-15

This memo replaces the old assumption that the complete `next` integration
history can be turned into one 17--19 patch KVM-v2 series.  It cannot.  Against
Linus commit `58717b2a1365d06c8c64b72aa948541b53fe31eb`, the current branch has
275 commits and its major components have grown into independently reviewable
projects:

| Component | Current integration footprint |
| --- | ---: |
| backend contract + seccomp + KVM-v2 | 38 files, 16,222 insertions |
| KVM-v2 directory alone | 24 files, 14,621 insertions |
| Vector2 kernel and selftest surface | 39 files, 10,681 insertions |
| `umlctl` and UML selftests | 400 files, 58,855 insertions |

These numbers are scope alarms, not patch-size targets.  Generated reports,
historical design records, test evidence, and operator tooling are useful on
the fork but do not belong in the initial kernel series.

## Non-negotiable rules

1. `next` stays the continuously integrated product branch.  No submission is
   generated by formatting its consolidated commits.
2. Every upstream series starts from the then-current Linus `master` in a clean
   worktree and is rebuilt by semantic extraction.
3. Every commit builds, and every behavior-changing commit carries the smallest
   gate that demonstrates its contract.
4. Snapshot, record/replay, Vector2, pool/fork-server, and `umlctl` never ride in
   the initial KVM execution series.
5. The generic `mm/` and scheduler changes are separate patches only when their
   contracts can be justified without reference to an out-of-tree feature.
6. Evidence is commit-pinned.  Results from the integration branch are
   discovery evidence until repeated on the exact submission head.

## Emission sequence

### E0 — independent fixes and test-harness corrections

Send small fixes on their own merits.  Current candidates include the
warning-free snapshot build guard only when snapshot itself is in scope; the
CPython and mmap-stress harness corrections can be proposed separately if the
corresponding selftests are accepted.  Do not mix these with architecture RFCs.

The removed UML-only `exit_mmap()` RSS-counter reset is not an upstream patch:
it deletes integration-only code that never belonged in mainline.  Its value is
to make the fork honest before extracting any MM dependency.

### E1 — backend contract RFC

Goal: make the execution-backend seam reviewable while preserving the existing
seccomp behavior.  This is an architecture RFC followed by a narrow code series,
not a dump of the current abstraction.

Include only:

- the typed ops contract and validation rules;
- the arbiter and backend selection policy;
- the seccomp implementation of that contract;
- focused contract tests and concise user documentation.

Exclude KVM-v2, static-key optimization, profiles, snapshot, replay, and
launcher code.  Re-derive the patch count after extraction; the old advertised
12-patch map is input to the audit, not a promise.

Acceptance: each commit builds, the default seccomp boot is unchanged, both
static and dynamic configurations pass the contract suite, and the seccomp
performance delta stays inside the documented budget.

### E2 — minimal KVM-v2 execution RFC

Goal: answer one review question: can UML execute an ordinary userspace process
through KVM while retaining the established UML host-process model?

Include only the load-bearing path:

- `/dev/kvm` capability negotiation and VM/vCPU lifecycle;
- curated CPUID and architectural state setup;
- memory-slot and CR3/TLB coherence required for correctness;
- syscall trap entry/exit and register marshalling;
- the minimum exception/FPU/TLS handling needed by the stated workload;
- focused KUnit, smoke, MM-churn, dynamic-loader, and CPython tier-0 tests.

Defer the in-guest syscall gadget unless measurements and review show that it is
essential to the minimal design.  Explicitly exclude APERF/MPERF, state tracing,
snapshot, snapshot ELF, record/replay, fork-server, pool, and all launcher
features.  The present `vcpu.c` and `syscall_trap.c` must be decomposed during
extraction; their integration sizes are not reviewable patch boundaries.

Acceptance: warning-free GCC and Clang builds, real `/dev/kvm` boot, seccomp
fallback, KVM smoke, bounds, MM-churn, dynamic loader, userspace smoke, and
CPython tier-0 on the exact submission head.  The cover letter must describe
KVM-v2 as an isolation and capability backend, not a blanket performance win.

### E3 — KVM-v2 snapshot follow-up

Include snapshot capture/restore and the ELF interchange surface only after E2
has a stable review direction.  Keep debugfs and mconsole control surfaces in
separate commits.  Require snapshot KUnit on real KVM memslots, restore smoke,
ELF round-trip, bounds tests, and a natural-duration soak.

### E4 — experimental deterministic record/replay RFC

Keep this explicitly experimental and bounded to the syscall and time surfaces
the implementation can reject safely.  Submit after snapshot so reviewers do
not have to reason about two state-serialization models at once.  Require strict
mismatch, external-I/O rejection, time payload, signal, and R/R-1 replay gates.

### E5 — Vector2 networking RFC

Vector2 is independent of the KVM backend and should be reviewed by the UML
networking audience on its own.  Start with the configuration grammar, lifecycle,
queue model, and one real transport.  Add TAP and multiqueue in follow-ups.
Performance evidence must compare the same host, backend, transport, and queue
count; current TCP parity evidence is useful but does not replace cross-host or
CPU-per-Gbit measurements.

Do not claim replacement of legacy vector until the transport keep-list and
migration syntax are decided.  `fd` and TAP are the currently proven runtime
transports; GRE/L2TP parsing is not a datapath claim.

### E6 — tools and operational integrations

`umlctl`, pool/fork-server, the syzkaller shim, framework examples, and soak
orchestration are userspace projects.  Publish them independently after the
kernel ABI they consume is accepted or clearly versioned.  Kernel cover letters
may cite them as external validation, but must not require reviewers to absorb
their implementation.

## Generic-code boundary

Two integration areas require special discipline:

- `mm/mmu_gather.c`: extract only after documenting the generic MM invariant,
  demonstrating a non-UML semantic justification, and testing architectures
  that use the affected path.  Otherwise redesign the UML side to avoid it.
- scheduler fork-worker support: treat it as a separate scheduler proposal with
  an independently useful API and tests.  Pool/fork-server convenience is not by
  itself sufficient justification for a generic scheduler hook.

No UML-specific counter repair belongs in `mm/mmap.c`.  The branch's former
`exit_mmap()` reset hid accounting drift after teardown; the current validation
removes it and tests the TLB/MM lifecycle instead.

## First concrete upstream worktree

After the post-Linus correctness fixes and natural soak are pinned, create only
the E1 extraction worktree.  Produce an inventory mapping every E1 hunk to its
integration source and label each as contract, mechanical seccomp migration,
test, or documentation.  Do not start E2 extraction until E1's review shape is
coherent; E2 is allowed to proceed on the fork, but its submission base must be
the reviewed E1 interface rather than today's private contract by assumption.
