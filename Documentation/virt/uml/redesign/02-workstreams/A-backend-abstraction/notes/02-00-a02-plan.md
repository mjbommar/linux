# A-02.0 — Scoping plan for the A-02 ptrace refactor

Date: 2026-04-17
Owner: claude-code session

## Context

A-02 ("Refactor existing skas mode into ptrace backend") is budgeted
at **6 weeks** in the workstream calendar — the largest single task in
workstream A. The spec lists 8 op categories to migrate in priority
order (hottest first):

1. `syscall_dispatch` (= our `run_userspace`)
2. `page_fault` (folded into `run_userspace` per A-01.2)
3. `context_switch`
4. `ipi_send`
5. `read_clock_ns`, `set_timer`
6. `mm_map`, `mm_unmap`
7. `host_io_submit` (no op today; deferred per A-01.2)
8. `read_guest_regs`, `write_guest_regs`

## Why this session does NOT do all 6 weeks

`05-validation/upstream-strategy.md` is explicit:

> Workstream A's first deliverable is 3-5 patches: the ops table
> header, one trivial ptrace op migration, and the conformance-suite
> skeleton. That's it.

Compressing 6 weeks of refactor into one session would:

- Produce a 50-patch megaseries that nobody will review (cf. the
  upstream-strategy.md "no 50-patch monsters" rule).
- Violate the bisectability requirement — each intermediate state
  must build and run.
- Miss the chance to course-correct after maintainer feedback on the
  scaffolding+first-op RFC.

## What this session does

The "first slice" of A-02:

| Subtask | Outcome |
|---|---|
| A-02.1 | Baseline build (regression reference) |
| A-02.2 | Minimal Kconfig stubs so backend.h compiles in real build |
| A-02.3 | `arch/um/backend/{ptrace,seccomp,common,contract}/` scaffolding |
| A-02.4 | `ptrace_ops` singleton with all 18 fields stubbed |
| A-02.5 | `init_backend()` arbiter wired in |
| A-02.6 | One cold-op migration end-to-end: `read_persistent_clock_ns` |
| A-02.7 | Conformance suite skeleton with one kunit test |
| A-02.8 | Post-change build verification |
| A-02.9 | checkpatch + sparse + smatch pass |
| A-02.10 | Workstream README updated; remaining ops queued as A-02.HOT-* and A-02.COLD-* tasks |

This produces the "first 3-5 patches" upstream-strategy calls for:

1. `um: backend: add ops table header` (already landed in A-01)
2. `um: backend: introduce arch/um/backend/ scaffolding`
3. `um: backend: add init_backend() arbiter`
4. `um: backend: migrate read_persistent_clock_ns to ops table`
5. `um: backend: bootstrap conformance test kunit suite`

Subsequent sessions take one HOT op at a time (~1-2 wk each), per
the spec priority order, each as its own 2-3 patch series.

## Why `read_persistent_clock_ns` for the proof-of-concept op

Smallest possible migration that exercises every part of the
contract:

- Single function. No per-mm or per-thread state.
- Called once at boot, not in any hot path.
- No backend-shared infrastructure needed (`common/` not exercised).
- Easy to unit-test ("returns a positive monotonic-ish value").
- If this doesn't work, nothing else will.

The spec lists this as item 5 in priority order ("hot path first"),
but for the *first slice*, "easiest to validate the contract" beats
"hottest" — once we know the dispatch path works end-to-end, hot ops
can land with confidence.

## Risk: scope creep

The 02-ptrace-refactor.md spec itself flags this as the biggest
risk. Mitigation: the 11 subtasks above are dependency-chained;
A-02.10 explicitly stops the session and queues follow-up work
rather than continuing past the first slice.

If the work is going faster than expected, the next op to consider
is **`read_clock_ns`** (also cold-ish, single function, similar
shape) — but only after the first slice has been verified end-to-end.
