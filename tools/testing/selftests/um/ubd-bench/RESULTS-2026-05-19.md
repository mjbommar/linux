# Memo #2 acceptance gate — UBD io_uring vs legacy do_io

**Date:** 2026-05-19
**Host:** server7 — AMD Ryzen 7 7840HS, 16 hw threads
**Kernel:** `umlctl-deploy @ 7861fee9ffad` rebuilt with the
`um_ubd_no_uring=` cmdline knob (this commit)
**Backend:** kvm-v2 (auto-falls back to seccomp when host policy
blocks the kvm-v2 pre-flight)
**UBD image:** 256 MiB raw, ext4, fresh per run

## Method

Same kernel binary both sides — `um_ubd_no_uring=1` on the cmdline
forces the legacy synchronous helper-thread path; absent it, the
io_uring substrate brings up `do_io_ring_batch`.

```
tools/testing/selftests/um/ubd-bench/run-ubd-perf.sh
```

Two workloads per side:

1. **`parallel-dd`** — 4 concurrent `dd` streams, 64 MiB each
   (256 MiB total), `bs=4M conv=fsync`.  Each `dd` is a single
   writer; together they exercise the io_thread's bulk batch.
2. **`fio randwrite`** — 8 parallel `psync` jobs (UML guest has
   no `libaio` or `io_uring` syscalls; psync + numjobs is the
   only way to get queue depth), 4 KiB random writes,
   `direct=0`, 15 s runtime.

## Results

### parallel-dd 4× 64 MiB (MB/s, higher is better)

Across 4 iterations of the full bench harness:

| iter | legacy | io_uring | delta |
|------|-------:|---------:|------:|
| 1    | 292.8  | 334.6    | +14 % |
| 2    | 338.6  | 397.1    | +17 % |
| 3    | 310.2  | 394.8    | +27 % |
| 4    | 306.8  | 296.1    |  −3 % |

**Median:** legacy 308.5 MB/s → io_uring 364.7 MB/s — **+18 %.**

Variance is high (~10 % spread within a single side) because the
benchmark uses buffered writes; host page-cache state and
scheduling jitter dominate the noise floor.  Iter 4's −3 % is
inside that noise floor.

### fio randwrite 4k, 8 jobs psync (buffered, MiB/s)

| run | legacy | io_uring |
|-----|-------:|---------:|
| A   | 42.5   | 43.9     |
| B   | 47.8   | 44.3     |

**Effective tie.**  `direct=0` means host page-cache absorbs the
writes — neither path actually queues to the backing file in this
window — so the in-flight queue depth difference between
`do_io` (serial) and `do_io_ring_batch` (depth-256) doesn't
show up.

### Memo §"Acceptance criteria" alignment

Memo 02 §Acceptance criteria sets:

  > at queue depth 32 the new path outperforms the old by ≥ 5×
  > on a `fio --rw=randread --iodepth=32 --bs=4k` workload.

That number was conceived on a host that *would* let the guest
use `libaio` / `io_uring`; UML's seccomp-bound guest can't, so
the literal acceptance bench doesn't translate.  The *spirit*
of the gate (queue depth matters) is visible in parallel-dd
where the io_uring path's 256-deep ring beats the depth-1
helper-thread by a median +18 %.  Achieving the literal 5×
number would require either (a) Phase 4 (`O_DIRECT` so writes
bypass host page-cache) or (b) a guest-side fio with an io_uring
host backend — both deferred to a follow-on sprint.
