# Expected-failure allowlist for the full CPython stdlib regrtest under UML.
#
# Host dependencies: install `python3.14-venv` (Debian/Ubuntu) on the host.
# UML uses hostfs to mount the host's `/`, so the guest sees whatever the
# host has installed.  Without python3.14-venv, both test_ensurepip and
# test_venv fail at import time (`ModuleNotFoundError: ensurepip`).
#
# Run-to-run variance: this suite is timing-sensitive under UML.  Observed
# failure counts (post-fixes) range from 7 (cleanest kvm-v2 run) to 18
# (worst flaky seccomp run).  test_threading, test_multiprocessing_*,
# test_concurrent_futures, test_faulthandler routinely time out under
# system load and cascade into regrtest's rerun-mode which can extend
# the run to 50+ min.  This is a real UML perf gap, not a correctness
# issue; workers that finish do produce correct results.
#
# Reference timings:
#
#   seccomp first-run baseline: 46,443 tests, 25 min 39 sec, 10 modules failed
#   kvm-v2  first-run baseline: 46,734 tests, 15 min 30 sec, 7 modules failed
#
# Catastrophic regressions previously seen:
#   - MM_ANONPAGES leak reports dropped to zero on both backends
#   - Suite-blocking segfaults became bounded to the spawn batch
#
# Common segfault count: 10 on each backend, all in
# test.test_multiprocessing_spawn.test_processes at python3.14[1133bc] addr=0x350
# (_Py_Dealloc reading per-thread interpreter pointer with NULL tstate).
# UML-only; same workload passes on alpine:edge python:3.14.3 in docker.
# Common to both backends, so this is not specific to the seccomp or
# kvm-v2 dispatcher.
#
# This file lists the UNION of failures across both backends.  Each entry
# is annotated with which backend(s) fail it, why, and where the issue
# actually lives.  Remove a line when the bug is fixed; the gate will catch
# any regression.
#
# Legend:
#   [seccomp+kvm] - fails on both backends
#   [seccomp]     - fails only on seccomp (kvm-v2 passes)
#   [kvm]         - fails only on kvm-v2 (would never happen with seccomp;
#                   no such cases in this ledger; kvm-v2 is a strict superset
#                   of seccomp passes here)

# [seccomp+kvm] test.test_asyncio.test_subprocess: test_devstdin_input
# (and possibly other subtests; the suite runs --quiet) fails its
# assertEqual(output, b'3').  The child reads /dev/stdin, which resolves
# via /proc/self/fd/0 to the asyncio stdin pipe -- an anonymous kernel
# pipe, no hostfs involved (contrary to an earlier note).  The minimal
# C process-model reproducer passes, so fork/exec/pipe/SIGCHLD is sound;
# the remaining failure looks like an asyncio transport/readiness timing
# interaction under seccomp and is not yet root-caused.  Run with -v to
# enumerate the exact subtests before attempting a fix.
test.test_asyncio.test_subprocess

# [seccomp+kvm] test_ensurepip fails because Debian/Ubuntu patch the
# system python to disable ensurepip.bootstrap() ("ensurepip is disabled
# in Debian/Ubuntu for the system python.").  UML mounts the host / via
# hostfs and inherits that policy; the same failure occurs on bare metal
# with the system python.  Host-side issue (use a python with ensurepip
# enabled), not a UML or arch/um limitation.
test_ensurepip

# [seccomp+kvm] test_no_newline asserts exact pyrepl cursor-movement
# escape codes.  UML's tty0 console is a tty (isatty() is true) but emits
# different cursor-positioning sequences than an xterm-compatible
# terminal, so the assertion mismatches.  Fails on any non-xterm
# terminal; not UML-specific.
test_pyrepl

# [seccomp+kvm] test_socket's UDP-Lite subtests (BasicUDPLITETest,
# SendmsgUDPLITETest, ...) fail because UDP-Lite was retired from the
# Linux kernel (commit 56520b398e5e "ipv4: Retire UDP-Lite.", v7.1):
# net/ipv4/udplite.c is gone, so socket(AF_INET, SOCK_DGRAM,
# IPPROTO_UDPLITE) now fails on ANY current kernel.  CPython 3.14 still
# exposes IPPROTO_UDPLITE and gates these tests on the constant existing
# (skipUnless HAVE_SOCKET_UDPLITE), not on kernel support, so setUp
# raises and the threaded teardown reports a cascade AttributeError on
# self.cli.  This is an upstream kernel change, not a UML limitation,
# and is not fixable in arch/um; the bulk of test_socket passes.
test_socket

# === seccomp-only failures (kvm-v2 passes these) ===

# [seccomp] test_itimer_virtual hangs until regrtest's 300s watchdog
# fires.  ITIMER_VIRTUAL (CPUCLOCK_VIRT) fires off task utime, but the
# seccomp backend never advances guest utime: SIGALRM ticks that
# interrupt guest userspace are dropped by the no-op SIGALRM case in
# arch/um/backend/seccomp/trap_user.c, and kernel-half ticks are charged
# to stime because os_in_kvm_run() is 0 on non-kvm-v2 backends.  With
# utime stuck at 0, SIGVTALRM never arrives and the busy loop never
# breaks.  kvm-v2 passes (CONFIG_UM_BACKEND_KVM_V2_ITIMER_VIRTUAL
# supplies the accounting).  An opt-in seccomp fix now exists --
# CONFIG_UM_BACKEND_SECCOMP_ITIMER_VIRTUAL (default n) -- which charges
# the guest-userspace tick to utime via account_process_tick(); enabling
# it makes test_itimer_virtual pass (validated: SIGVTALRM 0 -> 9).  It is
# off by default because it leaves a pure-userspace workload with an
# approximate ~50/50 utime/stime split, so the default build still fails
# this test and it stays allowlisted.  Enable the option (or run on
# kvm-v2) to pass it.
test_signal
