# umlbuild — design spec

**Status:** draft 1, 2026-05-23
**Sibling of:** `umlctl` (lifecycle CLI)
**Goal:** produce reproducible UML instances — kernel binary + rootfs
ubd image + a generated `Umlfile.toml` that `umlctl up` can boot.

## Why a separate tool

`umlctl` runs an *already-built* UML instance: kernel binary + rootfs
exist on disk, `umlctl up -f Umlfile.toml` wires them into a running
guest. Today, building those inputs is a manual `make ARCH=um O=...`
loop plus ad-hoc disk-image hacking. `umlbuild` makes that step a
first-class, scriptable, idempotent operation.

## Constraints inherited from umlctl

These are non-negotiable; `umlbuild` is the sibling, not the rebel.

- **Same crate, third `[[bin]]`.** Add to
  `tools/uml/uml-launcher/Cargo.toml`; code lives at
  `src/bin/umlbuild/`. No new dependencies unless we can't avoid them.
- **Clap derive** for CLI parsing, with `env` + `wrap_help` features.
- **`anyhow::Result`** for errors; `eprintln!("umlbuild: {e:#}")` at
  exit; `bail!()` for validation failures.
- **`tracing` + `tracing-subscriber`** for logging. `-v / -vv / -vvv`
  flags, `RUST_LOG` env var, `--log-format plain|json`.
- **`figment`** for any layered config we read (CLI > env > TOML >
  defaults). `toml` crate for emission.
- **One file per subcommand** under `src/bin/umlbuild/`.
- **XDG layout** for cache + state. The kernel-build O= tree and the
  downloaded base tarballs live under `$XDG_CACHE_HOME/uml-build/`
  (default `~/.cache/uml-build/`).

## Subcommand surface

Five verbs total. Each is independently runnable; `instance` is the
end-to-end orchestrator.

```
umlbuild kernel    --profile mvp [--out PATH] [--strip]
umlbuild rootfs    --profile sandbox [--out DIR]
umlbuild image     --rootfs-dir DIR --out PATH --size 200M
umlbuild instance  --profile sandbox --out DIR
umlbuild profile   list | show <name>
```

### `umlbuild kernel`

Inputs:
- `--profile <name>` — one of the built-in profiles or a path to a
  profile TOML.
- `--source <path>` — kernel source tree (default: walk up from CWD
  looking for `arch/um/Kconfig`).
- `--out <path>` — where to put the resulting kernel binary. Default:
  `$XDG_CACHE_HOME/uml-build/kernels/<profile>/linux`.
- `--strip` — `strip` the binary after build (saves ~500 KB).
- `--jobs <N>` — passes to `make -j`. Default: host CPU count.

Behavior:
1. Resolve the profile's `[kernel]` section: starting config
   (`tinyconfig` / `base_defconfig` / explicit path) and the list of
   `--enable` / `--disable` Kconfig diffs.
2. Set up `O=<cache>/builds/<profile>/` (NEVER builds in-tree —
   matches the user's standing `O=` discipline rule).
3. `make ARCH=um O=$O <base_config>`, then loop over enables/disables
   via `./scripts/config --file $O/.config --enable X --disable Y`.
4. `make ARCH=um O=$O olddefconfig`, then `make ARCH=um O=$O -j$N`.
5. Optional `strip $O/linux`.
6. Copy/link to `--out`, write a sidecar `linux.sha256` and
   `linux.config.sha256`.
7. Reproduction manifest: write `$out.manifest.toml` capturing the
   exact profile content + source HEAD + toolchain version.

Idempotence: if `linux.config.sha256` matches the would-be config, skip
the build entirely. Force rebuild with `--force`.

### `umlbuild rootfs`

Inputs:
- `--profile <name>` — same profile TOML; rootfs section selects base
  + package set.
- `--out <dir>` — staging directory (will hold the populated
  filesystem tree). Default:
  `$XDG_CACHE_HOME/uml-build/rootfs/<profile>/`.
- `--cache <dir>` — where downloaded base tarballs live. Default:
  `$XDG_CACHE_HOME/uml-build/dl/`.

Behavior — two base flavors at v1:

**Alpine path** (`base = "alpine"`):
1. Download
   `alpine-minirootfs-<version>-x86_64.tar.gz` from a pinned URL.
2. Verify sha256 against the value in the profile.
3. Extract into `$out/`.
4. Bind-mount nothing — instead, populate `/etc/resolv.conf` from host
   and `chroot $out apk add --no-cache <packages>` to layer in
   tooling. (chroot needs uid 0 — see "Privilege model" below.)
5. Install `/sbin/init` from the rendered init template.
6. Strip `/var/cache/apk/*` and any temporary files.

**Debian-slim path** (`base = "debian-slim"`):
1. `mmdebstrap --variant=minbase --components=main bookworm $out` (no
   sudo required when using `--mode=unshare`).
2. Layer `apt-get install --no-install-recommends <packages>` inside a
   `chroot`.
3. Install `/sbin/init` template.
4. Apt cleanup: `apt-get clean && rm -rf /var/lib/apt/lists/*`.

The `/sbin/init` template is generated by `umlbuild`, not pulled from
the host. Contract: it reads `/proc/cmdline` for `sandbox.cmd=...`,
drops to uid 1000 if `sandbox.user=` is set, mounts standard pseudo-fs
(`/proc`, `/sys`, `/dev/pts`, `/dev/shm`, `/tmp`), exec's the
sandbox command, copies stdout/stderr to a fixed path under `/results/`
(tmpfs), and `poweroff -f` when done. Mirrors `umlctl`'s
`render_init_script` shape closely.

Output: a populated directory tree, plus `$out.manifest.toml` capturing
base + version + sha + package list.

### `umlbuild image`

Inputs:
- `--rootfs-dir <dir>` — directory tree to pack.
- `--out <path>` — destination ubd image file.
- `--size <size>` — image size (e.g. `200M`, `2G`). Validated; refused
  if smaller than the rootfs's `du -sb`.
- `--fstype <ext4|ext2>` — default `ext4`. (Future: `squashfs` for RO.)
- `--label <name>` — filesystem label. Default: `uml-sandbox`.

Behavior:
1. `du -sb $rootfs_dir` → required minimum.
2. `truncate -s $size $out` to allocate sparsely.
3. **`mkfs.ext4 -F -L $label -d $rootfs_dir $out`** — populates the
   filesystem from the host directory *without any loop mount* and
   *without sudo*. This is the linchpin that keeps the tool usable in
   sandboxes and CI.
4. `e2fsck -fn $out` for self-check (read-only fsck; refuses to
   modify).
5. Write `$out.manifest.toml` with size + label + sha256 of input
   directory's tar.

Output: a ubd-attachable image, ready for
`ubd0=$out` on the kernel command line.

### `umlbuild instance`

The orchestrator. Inputs:
- `--profile <name>`
- `--out <dir>` — destination directory; will contain `linux`,
  `rootfs.img`, `Umlfile.toml`, and manifests.

Behavior:
1. Run `umlbuild kernel --profile $p --out $out/linux`.
2. Run `umlbuild rootfs --profile $p --out $out/rootfs.d`.
3. Run `umlbuild image --rootfs-dir $out/rootfs.d --out $out/rootfs.img --size <from profile>`.
4. Render `$out/Umlfile.toml` — a complete schema_version=1
   `Umlfile` pointing `kernel.path` at `$out/linux` and adding a
   `[[volumes]]` (or a synthesized `--ubd0=...` append line) for
   `$out/rootfs.img`.
5. Echo the next-step command:
   `umlctl up -f $out/Umlfile.toml`.

End-to-end test (becomes the kselftest gate): `umlbuild instance
--profile mvp --out /tmp/uml-mvp && umlctl up -f
/tmp/uml-mvp/Umlfile.toml` must complete `cpython-tier0` from inside
the ubd-rooted guest.

### `umlbuild profile {list|show}`

`profile list` enumerates the built-in profiles and any user-provided
TOMLs found in
`$XDG_CONFIG_HOME/uml-build/profiles/*.toml`.

`profile show <name>` pretty-prints the resolved profile (after
inheritance, if profiles support `extends = "..."` — see "Open
questions").

## Profile schema

A `umlbuild` profile is a single TOML, paralleling the `Umlfile.toml`
shape but describing *how to construct* rather than *how to run*.

```toml
schema_version = 1

[profile]
name = "mvp"
description = "Minimum viable UML that runs python3 cpython-tier0"

[kernel]
# Starting point. One of:
#   - "tinyconfig"
#   - "base_defconfig"
#   - "x86_64_defconfig"
#   - { path = "arch/um/configs/x86_64_defconfig" }   (explicit path)
base_config = "tinyconfig"

# Kconfig overlay. Order matters: enables apply first, then disables.
enable = [
    "64BIT",
    "PRINTK",
    "NULL_CHAN",
    "HOSTFS",
    "BINFMT_ELF",
    "BINFMT_SCRIPT",
    "PROC_FS",
    "UM_WORKER_PROCESS",
    "STDERR_CONSOLE",
    "FUTEX",
]
disable = []

# Strip the resulting binary.
strip = true

[rootfs]
# Either "alpine" or "debian-slim" at v1.
base = "alpine"

[rootfs.alpine]
version = "3.20.3"
sha256  = "beefdeadbeefdead..."   # of the minirootfs tarball
# Mirror to download from. Default: dl-cdn.alpinelinux.org.
mirror  = "https://dl-cdn.alpinelinux.org/alpine"

packages = ["python3", "busybox-extras", "ca-certificates"]

[image]
size   = "200M"
fstype = "ext4"
label  = "uml-mvp"

[instance]
# Defaults baked into the emitted Umlfile.toml.
mem     = "256M"
ncpus   = 1
backend = "seccomp"
# What runs at boot. The init template reads sandbox.cmd= from
# /proc/cmdline, so this populates [kernel].append in the Umlfile.
sandbox_cmd = "python3 -c 'print(\"hi from umlbuild\")'"
sandbox_user = "sandbox"   # /sbin/init drops to this uid
```

Built-in profiles to ship at v1 (under
`tools/uml/uml-launcher/profiles/`):

- `mvp.toml` — 11-Kconfig minimum from the
  2026-05-23-minimum-viable-uml diary. Runs cpython-tier0.
- `sandbox.toml` — `mvp` + NET, INET, TMPFS, DEVTMPFS, DEVPTS,
  OVERLAY_FS. The "safe but useful for real code" target.
- `dev.toml` — base_defconfig. The everyday development build.
- `container.toml` — base_defconfig + container fragment (the
  yesterday's docker-in-UML build, ~110 MB).

## Privilege model

**The hard rule:** `umlbuild` must work without `sudo` on the happy path.

- **Kernel build:** no privilege needed. `make ARCH=um O=...` is plain
  userspace.
- **Image creation:** `mkfs.ext4 -d` is the *only* path that pops
  this rule open. No loop-mount, no `chroot` for image filling.
- **Rootfs population:** Alpine `chroot` to `apk add` *does* need uid
  0 inside the chroot. Two options:
  1. **Default:** require host uid 0 (or `sudo`) only for the
     `chroot apk add` step, and fail loudly otherwise.
  2. **`--rootless`:** drive `apk` from the host directly with
     `--root $rootfs --no-chown --keys-dir /etc/apk/keys`, avoiding
     the chroot. Alpine's `apk` supports this since 2.10.

  v1 ships option (2) wherever possible; falls back to (1) with a
  clear error message if it can't.
- **Debian path:** `mmdebstrap --mode=unshare` runs entirely rootless
  via user namespaces. No sudo.

## File layout (cache, state, profiles)

Following the umlctl XDG conventions:

```
$XDG_CACHE_HOME/uml-build/         # ~/.cache/uml-build by default
├── dl/                            # downloaded tarballs (pinned by sha)
│   └── alpine-minirootfs-3.20.3-x86_64.tar.gz
├── builds/                        # kernel O= trees
│   └── mvp/   (the actual O= dir; vmlinux, .config, etc.)
├── rootfs/                        # staged rootfs trees
│   └── mvp/   (populated directory ready for mkfs.ext4 -d)
└── images/                        # finished ubd images
    └── mvp.img

$XDG_CONFIG_HOME/uml-build/        # ~/.config/uml-build by default
└── profiles/                      # user-provided profile TOMLs
    └── custom-thing.toml

tools/uml/uml-launcher/profiles/   # in-tree profiles
├── mvp.toml
├── sandbox.toml
├── dev.toml
└── container.toml
```

## What umlbuild does NOT do (yet)

- **Run kernels.** That's umlctl's job. `umlbuild instance` emits a
  Umlfile.toml; `umlctl up -f` does the actual running.
- **Update the kernel source tree.** No `git pull`, no patching.
- **Cross-compile.** Host arch only at v1.
- **Sign images.** Future. The manifest sha256 is the only attestation.
- **Push to a registry / pull from one.** Local-only at v1.
- **Diff / inspect** running instances. Future.

## Open questions

1. **Profile inheritance.** Should `extends = "mvp"` let the
   `container` profile inherit and override? Cleaner for users, but
   complicates the resolution logic. Defer to v2.

2. **Should umlbuild own the kernel source path discovery?** Today
   `umlctl` discovers via `${UML_KERNEL}` env or `--kernel` flag. For
   the build side, we have to know *where the source is*. Three
   options: (a) require `--source <path>`, (b) walk up from CWD until
   we find `arch/um/Kconfig`, (c) require an env var
   `UMLBUILD_SOURCE`. I'd say (b) for ergonomics, with (a) as the
   explicit override.

3. **Manifest format.** Use the same TOML+sha256 sidecar everywhere,
   or invent a `umlbuild.lock` that captures *all* inputs (profile +
   source HEAD + toolchain + tarball shas)? The lockfile is nicer
   for reproducibility audits but is more code. Start with sidecars,
   add a lockfile if users ask.

4. **Test gate location.** Goes under
   `tools/testing/selftests/um/umlbuild/` (kselftest convention) with
   `Makefile`, `run-umlbuild-smoke.sh`, and an expected-output file.
   The CI gate is: build `mvp` profile end-to-end and pass
   `cpython-tier0` inside the ubd-rooted guest.

5. **Should we fix the Makefile install bug?** The existing
   `tools/uml/uml-launcher/Makefile` installs only `uml-launcher`,
   not `umlctl`. While we're adding a third binary, fix the
   install target to ship all three.

## v1 ship list

In order, each commit lands a working slice:

1. `umlbuild kernel` + `mvp.toml` profile. Selftest: builds the
   exact same 2.41 MB binary the diary produced.
2. `umlbuild rootfs` + Alpine path. Selftest: produces a 30 MB
   populated tree containing `/usr/bin/python3`.
3. `umlbuild image`. Selftest: produces an ext4 image that mounts
   read-write inside a guest and contains the rootfs.
4. `umlbuild instance` + emitted Umlfile. Selftest: `umlbuild
   instance --profile mvp && umlctl up` runs cpython-tier0 from
   inside the ubd image (not from hostfs).
5. `umlbuild profile {list,show}` + `sandbox`, `dev`, `container`
   profiles. Selftest: each profile's `instance` succeeds.
6. `Makefile` install fix + `USAGE.md` + signed-off commits.

Each slice is committable on its own; together they constitute v1.
